# The Funeral Stationery

A marketing/product frontend for a funeral stationery business, built on Next.js 16 (App Router), React 19, and Tailwind CSS v4. The design system comes from the redesign handoff in `funeral-stationery-handoff/` (`HANDOFF.md` is the spec, `source/*.dc.html` the page mockups) and is wired into `globals.css` as CSS custom properties consumed via Tailwind's `@theme inline`. It also includes a small server-side layer: a stationery design editor (`/design`) that generates print-ready PDF proofs via a headless-Chromium Route Handler — see **Proof Generation** below.

## Core Commands

- **Development:** `npm run dev`
- **Build:** `npm run build`
- **Start (prod):** `npm run start`
- **Linting:** `npm run lint`
- **Tests:** `npm test` (Vitest)
- **Database:** `npm run db:generate` / `db:migrate` / `db:push` / `db:seed` / `db:studio` (Drizzle Kit) — see **Data Layer** below.
- **Bulk templates:** `npm run templates:generate` — see **Bulk Template Generation** below.
- **Preview thumbnails:** `npm run templates:thumbnails` — re-render `preview_image_url` for templates already in the DB; see **Background Artwork** below.
- **Background artwork:** `npm run backgrounds:fetch` — see **Background Artwork** below.

There is still no `npm run typecheck` script — do not assume one exists. `npm run dev`/`npm run build` also drive the proof-generation Route Handler below; it needs no extra setup locally (Puppeteer downloads its own Chromium on `npm install`).

## Architecture & Tech Stack Rules

- **Framework:** Next.js 16 App Router (`src/app/`) with React 19. Server Components by default; add `"use client"` only where interactivity requires it.
- **Path alias:** `@/*` maps to `src/*` (see [tsconfig.json](tsconfig.json)).
- **Styling:** Tailwind CSS v4 via the PostCSS plugin — no `tailwind.config.*` file; theme tokens (colors, fonts, spacing, shadows) are defined as CSS custom properties in [src/app/globals.css](src/app/globals.css) inside `:root` and re-exposed through `@theme inline`. When adding a new design token, add it in both places, matching the naming in [funeral-stationery-handoff/HANDOFF.md](funeral-stationery-handoff/HANDOFF.md) (its `--text-2`/`--text-3`/`--text-label` are `ink-2`/`ink-3`/`ink-label` here, and its cover paper is `sheet` — `bg-cover` is already a Tailwind utility).
- **Design system:** Treat `HANDOFF.md` as the source of truth for color, type, spacing, radius, and elevation decisions — plum on warm paper, generous whitespace, 8/12/16px corners, soft plum-tinted shadows, 18px body copy and 44px+ touch targets because many customers are older. Match its intent before improvising new visual patterns. The shared pieces are component classes in `globals.css` (`type-body`, `type-hero`/`type-page`/`type-section`/`type-sub`, `site-container`, `btn` + `btn-primary`/`btn-outline`/`btn-ghost`/`btn-on-dark`, `chip`, `opt`, `field`, `eyebrow`, `link`, `cover`/`card-link`, and `table-stack` for a data table: one card per row, with each cell's `data-label`, when its own box is too narrow, never a sideways scroll) — use them rather than re-spelling the utilities. A redesigned page's `<main>` carries `type-body`.
- **No bare element selectors in `globals.css`.** The print canvas (`PageCanvas`, `/proof-render`) renders under the same stylesheet, so a global `p { text-wrap: pretty }` or a `body` font-size would re-break lines on the press PDF. Scope type rules to a class.
- **Legacy tokens are aliases.** The old Material-style names (`primary`, `primary-container`, `on-surface`, `surface-container-*`, `outline-variant`, `secondary`, ...) still exist in `globals.css`, mapped onto the new palette, so the pages the handoff doesn't cover (basket, checkout, account, order, the editor, `/admin`) follow the new colours without having been rewritten. New code uses the handoff tokens; note `surface` now means a **white card** and the page background is `paper`.
- **Fonts:** `Newsreader` (headings, prices, quotes — `font-display`) paired with `Work Sans` (body/UI, `font-body`), plus every face in the editor's picker, all **self-hosted** in `src/fonts/` (woff2 files + a generated `fonts.css` of `@font-face` rules and `--font-*` variables on `:root`), imported by [src/app/layout.tsx](src/app/layout.tsx); `globals.css` builds `--font-display`/`--font-body` from `--font-newsreader`/`--font-work-sans`. **Don't go back to `next/font/google`**: Google intermittently serves extensionless `/l/font?kit=…&skey=…` URLs that fail the build in both bundlers (vercel/next.js#99114), and with ~50 families nearly every build hit one. `next/font/local` won't do either — it can't give each subset file its own `unicode-range`, so accented names would print in a fallback face. To add or change a font, edit `FONTS` in `scripts/vendor-fonts.ts` and run `npx tsx scripts/vendor-fonts.ts` (it requests the CSS exactly as next/font did, so the files are the same ones). `Source Serif 4` (the previous heading face) stays as `--font-source-serif` because it is the editor's "Source Serif" option — don't point that option back at `--font-display`, or every saved design in it would print in Newsreader.
- **Business facts live in [src/lib/site.ts](src/lib/site.ts)** — phone, email, hours, address, the order cut-off, the turnaround wording and the Trustpilot profile. Never retype them in a component; several are still open questions for the owner (see the handoff), and one edit there must change every page. That includes the database's copy: a delivery option's note (edited in `/admin`) writes `{cutoff}`, never a time, and `getListPricingData` fills in `ORDER_CUTOFF` (`withOrderCutoff`) — a typed "11am" there once contradicted the 10am everywhere else, so `optionNoteError` refuses a time or an unknown `{token}` in an admin-saved note. The cut-off line reads "Order by 10am on a working day for next-working-day delivery" wherever it appears; keep "on a working day" — nothing is collected at weekends. Print time is "printed within `PRINT_TURNAROUND`", never "standard turnaround": "Standard" is the free delivery option's name.
- **Icons:** `lucide-react`.
- **Components:** Presentational components live in `src/components/` as top-level, PascalCase files (e.g. `Header.tsx`, `Hero.tsx`). No nested component directories yet — keep new components flat unless a section grows enough to warrant a subfolder.

## Proof Generation

The `/design` editor (`src/components/DesignEditor.tsx`) builds a `DesignDoc` (see `src/lib/designEditor.ts`) — pages of percentage-positioned text/photo/shape/clipart/frame elements. To turn that into a print-ready PDF, `POST /api/proof` (`src/app/api/proof/route.ts`):

1. Launches headless Chromium and navigates to the hidden, `noindex` route `/proof-render` (`src/app/proof-render/page.tsx` → `ProofRenderClient.tsx`), which renders the **same** `PageCanvas` component the live editor uses (`src/components/PageCanvas.tsx` — its own module so the design page's gallery and `/proof-render` don't ship the whole editor), fed via `window.__PROOF_DATA__`.
2. Waits for `document.fonts.ready`, all `<img>` elements to load, and two stable animation frames, signalled back via a `data-proof-ready` attribute — never screenshot before this fires.
3. Prints the page through Chromium's own printer (live text, embedded fonts) with an `@page` the size of the **document's own** trim plus bleed (`pageMetrics(docTrim(doc))` — see **Product Formats**), then `pdf-lib` checks each sheet's size and draws crop marks at the trim line.

This exists specifically so the PDF is guaranteed pixel-identical to what the customer saw on screen — never reimplement the layout/font-rendering logic as a second renderer (e.g. drawing shapes/text directly with `pdf-lib`); always route new export formats through screenshotting the real component.

**Local vs production Chromium:** `puppeteer` (devDependency, downloads a real Chromium locally) is used when `process.env.VERCEL` is unset; `puppeteer-core` + `@sparticuz/chromium` (Linux-only) is used on Vercel. `next.config.ts`'s `outputFileTracingExcludes` keeps the dev-only package out of the deployed function, and its `outputFileTracingIncludes` adds `@sparticuz/chromium/bin` (the compressed browser, which the tracer can't see) to every route in `CHROMIUM_ROUTES` (`src/lib/chromiumRoutes.ts`) — a new route that reaches `launchHeadlessBrowser` must be added there, and `chromiumRoutes.test.ts` fails until it is. **Requires Vercel Pro or higher** — the route's `maxDuration` exceeds the Hobby plan's 10s ceiling.

## Data Layer

Drizzle ORM + MySQL 8 (`mysql2` driver). Schema lives in `src/db/schema/*.ts`, the client in `src/db/index.ts` (`db`, an HMR-safe pooled singleton — throws if `DATABASE_URL` is unset).

- **The DB is the runtime source of truth for the catalogue.** `src/lib/catalogue.server.ts` (products/categories/templates, `is_active`/`status='published'`/`sort_order` respected) and `src/lib/pricing.server.ts` (the five option tables → the pure `PricingData` shape) load it server-side and pass it to client components as props; `src/lib/templates.ts` and `src/lib/orderOfServicePricing.ts` now hold only types and pure functions (`filterTemplates`, `getQuote(data, selection)`, `defaultSelection`, `cheapestQuote`, `formatPence`). The quote engine computes in **integer pence**. `/`, `/shop`, `/products/[slug]`, `/products/[slug]/[template]`, `/design`, `/cart`, `/checkout` and `/orders` are `force-dynamic` for this reason. The old hardcoded arrays live on only as seed bootstrap data in `src/db/seedCatalogue.ts` — never import them at runtime.
- **Surrogate int PKs for catalogue/pricing rows, UUID PKs for user data, slug snapshots for orders.** `products`, `template_categories`, `templates` and the pricing tables use an `int` autoincrement PK plus a unique `slug` column carrying the human-readable id already used in URLs (`order-of-service`, `silk`, ...) — small/fast to join, appropriate since these rows are only ever written by the seed script or the admin area, never an untrusted client. `users`, `designs`, `orders`, etc. use `char(36)` UUIDs (`crypto.randomUUID()`) instead, since those rows are created by real (or guest) visitors. `order_items`/`orders` spec columns go a third way: plain `varchar` **slugs with no FK at all** — see the snapshot point below for why.
- **A template belongs to exactly one product, not many.** `templates.product_id` is a plain FK (NOT NULL) — a template's starter content (cover/running-order/back-page via `makeStarterDoc`) is built for one product's format, so this is 1:1, not a join table. `src/lib/templates.ts`'s `Template.productId` mirrors this; there's no `ALL_PRODUCTS`/`PRINTED_KEEPSAKES` concept any more. Categories are still genuinely many-to-many (`template_category_links`) — a design can be both "floral" and "classic".
- **`src/lib/designs.server.ts` is the slug↔surrogate-id seam.** Every write resolves an incoming slug (from the URL, the editor, `Selection`) to its catalogue row's surrogate id before touching `designs`; every read joins back out to slugs. Nothing outside `src/db` ever sees a surrogate id — `SavedDesign.templateId`/`.productId`/`.pagesOptionId`/`.paperId` are always slugs.
- **Money is integer pence**, never floats (`vat_pence`, `unit_price_pence`, ...). Multiplier columns are `decimal(6,4)`.
- **Live rows reference the catalogue; order rows snapshot it.** `designs` FKs into the pricing tables (`paper_options`/`quantity_options`/`page_count_options`/`delivery_options`), each scoped by `product_id` with a composite FK on `(product_id, *_option_id)` — see `pricing.ts` for why each is its own table, not one polymorphic table (MySQL FKs must target an exact unique key). **There is no colour/ink axis, and don't reintroduce one** — the customer prints exactly what they see in the editor: the press PDF is printed from that same colour design, on its product's one artboard (see **Product Formats**). A "black & white" option could only charge for something the artwork never has. A different *shape* is a different product with its own artboard, not an option (the planned 210 × 210 square booklet is its own product). **Print sizes are the one exception, and only at the artwork's own shape**: `size_options` (A6/A5/A4 for the booklet) are a multiplier like paper, the design is drawn once at the product's trim and the press scales it — sound only because every A size has the same shape, so the same percentages scale exactly. `sizeFormatError` refuses a size of any other shape, and a size on a `sized_by_option` product (the memory board), whose page-count options *are* already its print sizes. Size is optional: a product with no rows prints at its trim and its `Selection.size` is `""`; with one active row the customer isn't asked. `order_items`/`orders` instead store the resolved spec as plain `varchar` **slug** snapshot columns with **no FK** — deliberately not the catalogue's surrogate int, since a surrogate id is meaningless once its row is gone but a slug like `"silk"` stays a readable historical record — plus a `quote_snapshot`/`doc_snapshot` JSON blob of exactly what the customer saw. A later catalogue or price change can never rewrite order history.
- **No cart table** — a cart is an `orders` row with `status = 'draft'`. See **Orders & Checkout** for the runtime rules.
- `src/db/seedData.ts` holds pure seed-row builders (no DB import, so they're unit-testable — see `seedData.test.ts`), fed from `src/db/seedCatalogue.ts` and keyed by `slug`/`*Slug` rather than a real FK, since a surrogate id doesn't exist until insert. `src/db/seed.ts` is the runner (`npm run db:seed`): it upserts each catalogue level, re-selects to build a slug→id map, and resolves the next level's FKs against it. `template_category_links` is delete-then-insert (not upsert) so a shrunk category list actually removes the stale rows, not just leaves them.
- **Seeding is bootstrap-only.** Once `products` has rows, `db:seed` exits without touching anything ("admin edits are authoritative") unless `SEED_FORCE=1` is set — a forced reseed reverts admin edits to labels/rates/multipliers/status, but never `templates.layout`, a product's trim/`template_pages` or a template's product (all deliberately excluded from the upsert's update columns — layouts and designs are drawn on them).
- `templates.layout` is nullable — null means "fall back to `makeStarterDoc()`". A non-null `DesignPage[]` is an admin-authored starter document (see **Admin Area**): `/design` instantiates it (fresh ids via `instantiateLayout`) for new designs, and applying such a template from the editor's picker replaces the whole document behind a confirm, while unauthored templates keep the old cover-only apply.
- **`templates.draft_layout` is the authoring working copy; `layout` is what customers get.** The authoring editor autosaves into `draft_layout` and *never* touches `layout`, so an admin can rework a live template without customers seeing half-finished pages. Null draft = no unpublished changes (**not** "no layout"); publishing copies `draft_layout` into `layout` and nulls it again. Nothing on the customer path reads `draft_layout` — keep it that way.
- **A booklet's template layout is exactly three pages: cover, middle, back** (`TEMPLATE_PAGE_COUNT` in `designEditor.ts`); a flat product authors its `products.template_pages` instead — front and back for a card or bookmark, the front alone for a board. This is the print shop's model — a booklet only ever needs those three, because the *middle* page is what repeats to fill whichever page-count option (4, 8, 12, 16, 20, 24) the customer picks. `withPageCount` performs that expansion: it holds page 0 and the last page fixed and grows/shrinks only the interior, repeating the middle page rather than blank-filling, and never truncating into the back page. `parseLayoutPages(pages, templatePages)` rejects any other length, the authoring editor hides the customer page-count picker and normalises older layouts on load via `toTemplateLayout`, so admins can't break the invariant. Don't reintroduce blank-fill or a "many distinct interior pages" concept — customer-side `instantiateLayout` still tolerates any stored length, but nothing should newly author one.
- `designs.doc` is the `DesignDoc` JSON blob. `ImageElement.src` holds an object-storage **URL**, not base64 — see **Photo Uploads** below.

## Product Formats

Each product has its own **format** — `products.size_label`, `trim_width_mm`/`trim_height_mm`, `template_pages` (1/2/3), `sized_by_option` and `paper_label` — loaded as `ProductFormat` (`toProductFormat`, `designEditor.ts`) on every `Product`. Today: the A5 booklet (148 × 210, 3 pages), A6 memorial and thank-you cards (105 × 148, front/back), 50 × 200 mm bookmarks (front/back) and the memory board (drawn at A4, one page, sized by option A4–A0, "Finish" instead of "Paper").

- **Every format is drawn at the same 3px/mm** (`PX_PER_MM`), so a font size means the same printed size on every product, and `PRINT_ZOOM` is one constant. Pixel geometry comes from `pageMetrics(trim)`; nothing draws from a fixed A5 constant any more (`PAGE_W_MM`/`FULL_BLEED_BOX` remain only for the A5-only generator and background pipeline).
- **A document carries its trim** (`DesignDoc.trim`, stamped from the product at creation; absent = A5, every pre-format design). `PageCanvas`/`StaticPage`/`BookletPreview`, `/proof-render`, the press PDF and the editor all read `docTrim(doc)`, so a saved design and an order's `doc_snapshot` render at their own size without asking the catalogue. A template layout stores no size — it's drawn on its product's trim, which is why the trim and `template_pages` **lock once a product has a template** (`adminUpdateProduct` 409s), and why a template **can't change product** once it has designs, or onto a different format once it has a layout (`adminUpdateTemplate` → `TemplateMoveError`, 409) — so a product with designs always has a template and stays locked. A new format is a new product.
- **Page-count options must fit the format** (`pageCountFormatError`): exactly 1 for a one-page product, exactly 2 for front/back, at least 4 for a booklet. The draft-layout seam (`adminSaveTemplateDraftLayout`) checks a layout's page count itself, so the generator and scripts can't bypass the route's check.
- **Enforced server-side**: `validateDesignPayload` rejects a doc whose trim isn't its product's, and the design routes refuse a template from another product (`templateProductSlug`). The editor's template picker only lists the design's own product's templates.
- **Customer copy reads the format** — `sizeText`, `lineSpec` (the basket/order/email spec line; a sized-by-option product shows its size option instead of its size label), `trimAspect`/`coverWidthFactor` (covers keep their shape at the A5 cover's height, so a bookmark isn't four times taller than a booklet). Don't retype "A5" in a component.
- **A sized-by-option product's press PDF is at its drawing trim** (A4 + bleed for the board), and so is a line ordered at a print size other than its artwork's (an A5 booklet ordered at A4); the admin order page and the Thintent job say what to scale it to (`pressScaleNote`). Only same-shape sizes may share a design this way. A6 scaled down from A5 keeps about 2mm of its 3mm bleed.
- **Print sizes (`size_options`) are a per-line choice**, priced as a multiplier, carried as `?size=` like copies, editable in the basket for a design line and fixed for an upload (its file was checked at that size — `evaluateArtwork` checks against the size chosen, photos included). `order_items.size_option_id` holds the slug; the quote snapshot's `size` freezes its dimensions (absent on older quotes — read it with `quoteSize`). A size other than the product's trim joins the Thintent product code (`order-of-service/a4/8/silk`) — the product's, not the artwork's, since an uploaded A4 file is drawn at A4; an A5 booklet's code is unchanged. A basket line's stored size is read as the size it prints at (`lineSizeSlug`): no size, or the trim's own size, follows sizes being switched on or off, so a basket isn't stranded, while any other retired size stays stale. The trim and `sized_by_option` can't change under a switched-on size (`formatSizesError`), and switching a size back on re-checks its shape. The "from £X" figure is priced at the default (first) size, where the price table and buy box start. Migration `0033` added the booklet's A5 (×1), A6 and A4; `0034` priced the booklet from the owner's own price list plus 15% (his old site's export — a table of totals, fitted to this model, so cells land within about ±15% of exactly +15%; A6 isn't on his list and is A5 less 20%) and moved copies to his breaks (15–500; 25 and 75 retired).
- The format is edited on `/admin/products/[slug]` (`AdminProductFormatForm`); migration `0013_new_products` set the formats, the memory board and placeholder pricing on existing databases.

## Shop Front

The customer's way in is **product first, design second, options third**: `/` and `/shop` lead to a product (`/products/[slug]`), which is the grid of that product's designs; a design opens its own page (`/products/[slug]/[template]`) where the options are chosen and priced; "Personalise this design" opens the editor. Styles (template categories) are a filter *inside* a product (`/products/[slug]?category=…`). A template belongs to exactly one product, so a style tile that spanned products would silently pick one — don't reintroduce cross-product theme tiles.

- **Only sellable products exist on the customer path.** `getSellableProducts()` (`catalogue.server.ts`) returns active products that have ≥1 published template *and* options on every pricing axis (`cheapestQuote` non-null), each carrying its first template's preview, its card blurb and occasion, and its cheapest configuration as the "from £X for N copies" figure. The home page, `/shop`, the header's Shop menu, the footer's Shop column, the contact form's topic list and `/products/[slug]` (404 otherwise) all read this one list, so a product half-configured in `/admin` is simply absent and appears by itself once complete. `getProducts()` (all active) remains for `/design`'s slug lookups.
- **The first sellable product leads.** The home hero, "Choose a design to begin" and the shop's full-width feature are whichever product sorts first (`products.sort_order`, set in `/admin`) — its label, design count, price and real covers. The hero headline is the only booklet-specific copy; nothing else names a product.
- **`products.description` and `products.occasion` are the per-product copy.** The blurb is the card text; `occasion` (`service` | `after`) is the shop page's filter and the header menu's grouping ("For the service" / "After the service"). Both are edited in `/admin/products`. There is no hand-written per-product page or slug-keyed copy map — if a product needs more bespoke text, add a column.
- **`Header.tsx` and `Footer.tsx` are server components** that load that list (`Header` renders the client `HeaderNav.tsx`) — every page renders `<Header />`/`<Footer />` unchanged, which is also why every page that renders them is `force-dynamic`. Keep both data-driven; don't hardcode product links again. The header is not sticky (the product page's filter bar is). "We design it for you" isn't a catalogue product: it's handled by a person and links to `/contact?topic=design-for-me` (`DESIGN_FOR_YOU_HREF` in `site.ts`). "Upload your own design" (`UPLOAD_DESIGN_HREF`) is the `/upload` flow — see **Upload Your Own Design**; on a product page its card adds `?product=` so the flow starts on that product.
- **`/products/[slug]` is the one product page for every product**: fact tiles, the filterable design grid (`ProductDesigns`), and a "Prices at a glance" table — copies × page counts on the default paper, computed with `getQuote` from the same `PricingData` the buy box uses, so the two can't disagree. `/order-of-service` is a permanent redirect in `next.config.ts`; `/templates` (the old cross-product browser) redirects to the product page, or to `/shop`.
- **`/products/[slug]/[template]` is the one design page.** `TemplateBuyBox` renders whichever axes the product's pricing tables hold as option buttons and hides an axis with a single option; `TemplateGallery` previews the design's cover / inside / back with the editor's own `PageCanvas` (never a second renderer), fed the template's `layout` — or `makeTemplateLayout` when it has none — with stand-in portraits filled in at render time only (`withPlaceholderPhotos`; the stored layout keeps its nulls). The URL's product and template must agree or it 404s.
- **There is no reviews page.** The business is on Trustpilot's free plan, whose only widgets are a badge and a "leave a review" button — no feed — so reviews are the home page's `Testimonials` section (`#reviews`; `/reviews` redirects there): Trustpilot's badge and the live Google reviews below. No hand-typed testimonials or reviews of any kind — the handoff's mockup had put invented words under real customers' names. **Never type the TrustScore or draw stars for it, and never copy Trustpilot review text onto the site** — Trustpilot's Legal Brand Guidelines allow a free account to show its score only through their widgets, and only paid plans may reuse review content. The home hero's rating line and the reviews section both carry Trustpilot's free "Micro Review Count" badge (`TrustpilotBadge.tsx`), loaded with Trustpilot's bootstrap script — the bare iframe alone only ever shows the fallback logo, because it waits for the script to answer a ping. The script and frame set no cookies and use no storage; the only cookie path is a split test joined via a `data-group` attribute, so never add one (that would need consent). `/privacy` says Trustpilot sees the visitor's IP, page, browser and language. Free accounts can't left-align the badge (`data-style-alignment` is a paid custom style), so the frame is sized to its text and pulled left to line up. New reviews are asked for on Google, not Trustpilot (see **Review Requests**).
- **The reviews section's cards are live Google reviews** (`ReviewsShowcase`, rules in the pure, tested `googleReviews.ts`, fetch in `googleReviews.server.ts`, served by `GET /api/google-reviews`). Google's Places terms drive the design: **nothing but the place ID may be cached or stored**, so there is no cache anywhere — the route is `no-store`, Next's fetch is `no-store`, avatars are plain `<img>` (next/image would store a copy) — and the section asks only when scrolled near (each ask is a paid Place Details Enterprise + Atmosphere call; the route is also rate-limited per IP; the hard cost ceiling is a daily quota on the key in Google Cloud). Each review shows its author's photo, name and profile link; the section credits "Google Maps", links the listing and says the order is Google's "most relevant". Show Google's five as returned — never filter out low ratings. The overall Google rating appears only from `GOOGLE_RATING_MIN_REVIEWS` (10) reviews. Google reviews are the only cards — never top them up with typed testimonials. A lone review is featured beside the heading; two or more go in a scroll-snapped carousel with a "1–3 of 5" pager (`reviewsLayout`, `carouselLabel`). Every review card carries Google's own grey "Google Maps" logo (`public/google-maps-logo.svg`, from Google's attribution assets — 16–19px tall, never redrawn) and a link to the review itself (`reviewUrl`, the review's `googleMapsUri`, which Google requires); carousel text is cut to five lines with "Read more" opening it on Google. Without `GOOGLE_PLACES_API_KEY`, or when Google doesn't answer, the section shows no cards.
- **`/trade` is the trade-account page for funeral directors**, linked from the utility bar ("Trade accounts", `TRADE_HREF`) and the footer (its "Ordering for families?" band above the columns — `<Footer tradeBand={false} />` on `/trade` itself — and the Help column). The application (`TradeApplicationForm` → `POST /api/trade`, pure and tested in `tradeApplication.ts`) is saved as a pending `trade_applications` row and approved or declined in `/admin/trade` (see **Trade Accounts**); the email to the contact inbox is a best-effort heads-up linking there. The save is what must work — a failed save is reported to the applicant — and like `/api/contact` it has the honeypot, per-IP limits and Turnstile, and isn't subscription-gated. The same address may apply again; the shop's email (never the applicant's answer) says when it's already on a firm. Its "what do you usually order" boxes are the sellable products plus "Something else". Keep the copy to what the site does: trade prices do appear once signed in, and checkout skips the card only for a firm switched on account. For someone signed in on a trade account the utility bar's link reads "Your trade account" (→ `/account`) and the footer band is hidden.
- **`/privacy` is the privacy and cookie notice.** Every cookie the site sets is listed in `SITE_COOKIES` (`siteCookies.ts`, names and lifetimes read from the modules that set them; `siteCookies.test.ts` pins them). All are strictly necessary, which is why there is no consent banner — adding anything that sets an optional cookie (a third-party widget, cookie-based analytics, an ad pixel) needs consent first, or a click-to-load. Business details in it come from `site.ts`; change its `LAST_UPDATED` with its wording.
- **`/contact` posts to `POST /api/contact`**, which validates with the pure, tested `src/lib/contact.ts` and emails the business via Resend with the customer as reply-to (`CONTACT_EMAIL`, falling back to `ORDER_NOTIFY_EMAIL`). Unlike order emails this is **not** best-effort — an unsendable message must be reported to the customer (503 without a mail provider or recipient), because otherwise they wait for a reply that never comes. The recipient is never customer-supplied; a hidden honeypot field is answered 200 without sending, and a per-IP limit (`src/lib/rateLimit.ts`, in-memory, so per instance) 429s before the catalogue query and again before the send. The page and the route build the topic list with the same `contactTopics()`.
- **The contact and trade forms carry Cloudflare Turnstile, set up the same way as the simple-print repo** (`@marsidev/react-turnstile` via `TurnstileCheck.tsx`; rules pure and tested in `turnstile.ts`; `verifyTurnstileToken` in `turnstile.server.ts`). Send stays off until the check passes; the token goes in the JSON body as `turnstileToken`, and the route checks it with Cloudflare after validation and before anything is emailed (a token is single-use, so the form starts a fresh check after every attempt). The public site key is **inlined** (`TURNSTILE_PRODUCTION_SITE_KEY`), never a build variable — simple-print kept getting the secret pasted into one; the secret is `TURNSTILE_SECRET_KEY` in Vercel, Production only. Only the production deploy uses the real pair (`NEXT_PUBLIC_TURNSTILE_LIVE`, set from `VERCEL_ENV` by `next.config.ts`); dev and previews use Cloudflare's always-pass test pair, so no hostname setup is needed for them. Production fails closed: a missing secret answers 503 "isn't available", and `next.config.ts` fails the production build while the site key is unset or looks like a secret. A new public form that sends anything gets the same check. `/privacy` names Cloudflare.

## Design Persistence

`/design` saves server-side; there is no `localStorage` fallback any more.

- **Ownership is an `Owner`: a signed-in customer or a guest.** `src/lib/session.ts` returns `{ userId, guestToken }` — the `tfs_user` cookie (see **Customer Accounts**) wins, else the httpOnly `tfs_guest` cookie it mints. Every query in `src/lib/designs.server.ts` is scoped by whichever half is set, so one visitor can never read or mutate another's design (a cross-owner fetch 404s rather than 403s — don't leak existence).
- **Routes:** `GET`/`POST /api/designs`, `GET`/`PATCH`/`DELETE /api/designs/[id]`. `DELETE` is a **soft** delete (`deleted_at`), so an `order_item` pointing at the design still reads.
- **Lazy creation.** Opening the editor does *not* insert a row. The first save (autosave or the Save button) POSTs, then swaps the new id into the URL with `history.replaceState`. Don't "fix" this into an eager insert — it would litter the table on every visit.
- **Validation lives in `validateDesignPayload`.** It enforces the page-count invariant (`doc.pages.length` must equal the chosen page-count option's `pageCount`, resolved from the DB via `getPageCountOption` in the routes, because `setPageCount` drives both). Option/template/product *existence* is enforced by the DB resolvers (`designs.server.ts`, `catalogue.server.ts`) — their `Unknown …` errors map to 400s in the routes. MySQL `CHECK` can't reach another table, so these are the only enforcement points — keep new spec fields validated there.
- Autosave is debounced 1.5s in `DesignEditor.tsx`; the Save button calls the same `persist()`.
- **Saves are revision-guarded** (`designs.revision`). A save that changes the design's content — doc, page count/paper, template (`changesContent`) — bumps it; the editor sends the revision it loaded, and a save from an out-of-date copy is refused with 409 `{ reason: "conflict" }` (`DesignConflictError`, `src/lib/designRevision.ts`), after which the editor stops saving and offers a reload — so a customer's open tab and an admin editing on their behalf can't silently overwrite each other. A rename alone neither checks nor bumps it, and the editor sends `name` only when it changed there, so renaming on `/account` never clashes with an open editor nor gets undone by one. Saves are queued one at a time (`createSerialQueue`), since two in flight would carry the same revision. On opening a saved design the editor fetches the latest copy and takes it up if it's newer and nothing has been edited yet — the Back button reuses the router's cached page, which would otherwise start a stale editor. A save with no revision (a tab opened before the column existed) is unconditional. The PATCH body is checked by `saveDesignPatch` (`designPatch.server.ts`), shared by the customer's and the admin's route; page count and paper are written only when sent.
- **A saved design opens on its own template, whatever its status** (`getTemplateForDesign`) — never a fallback, which would re-point it on the next save (or, across products, have every save refused). A new design takes its template's product; a valid `?product=` with an unknown template still opens that product, on its first template.

## Customer Accounts

Sign-in is by **emailed one-time link, no password, no provider** (`src/lib/auth.ts` pure + tested, `src/lib/auth.server.ts` the seam, `src/lib/userSession.ts` the cookie). Guests keep the frictionless flow; an account is what makes their work reachable from a second device or after the cookie is gone.

- **One account page, one way in.** `/account` holds sign-in (or "Signed in as … / Sign out"), My Designs and My Orders. The header's account button reads "Sign in" (→ `/account`) or, signed in, "My account" with a menu holding the account page and Sign out; a guest sees the sign-in form *above* what this browser has saved, so nothing hides behind a login. `/designs` and `/orders` redirect to it. Don't scatter sign-in prompts across other pages or the editor again — that was tried and removed as confusing.
- **Nothing is claimed on a typed address, only on a clicked link.** `POST /api/auth/login` writes a `login_tokens` row (sha256 of the secret, 15-minute expiry, its own `redirect_to`) and emails the link; `GET /api/auth/verify` spends it with one atomic conditional UPDATE (`consumed_at IS NULL`), finds-or-creates the `users` row *then*, sets `tfs_user` and calls `claimOwnership`. The login response is identical for known and unknown addresses. Don't attach `orders.user_id` at checkout from `contact_email` — typing a stranger's address must not pollute their account.
- **`claimOwnership` takes two things:** every row under the browser's guest token (designs, uploads, the basket — merged line-by-line into the account's existing draft, duplicates dropped) and every **paid** order whose `contact_email` is the email just proven, plus the designs on those orders. That second leg is how an order placed as a guest is found again from a phone.
- **Order links stay plain.** The confirmation email links to `/orders/[id]`; a guest who can't see it is redirected to `/account?next=/orders/[id]` (for every id, so it reveals nothing), and a signed-in stranger gets a 404. Don't turn the email link into a sign-in link — a single-use link breaks on the second click.
- **The session cookie is stateless HMAC** like `adminSession.ts`, keyed off `AUTH_SECRET` (30 days). Rotating the secret signs everyone out; that is the revocation lever. Outside production an unset `AUTH_SECRET` falls back to a fixed development secret, so accounts always work on `npm run dev` — an "accounts off" local state made the whole feature invisible. In production unset → `authConfigured()` is false, the routes 503 and the site is guest-only. Without Resend, development returns the link to the form, which shows it on screen. The sign-out route leaves the guest cookie alone: everything it owned moved to the account.

## Trade Accounts

Funeral directors order for families through a **trade account**: same sign-in, different `/account`. `src/lib/trade.ts` is pure and tested (validation, the greeting/date, the orders table's tabs and search); `src/lib/trade.server.ts` is the seam.

- **Detection is by email, nothing else.** Admins create a firm (`trade_firms`: name, payment terms, active) and list its people's emails (`trade_members`, lowercased, one firm per address) in `/admin/trade`. A customer signs in by emailed link exactly as before; `getCurrentTradeMembership()` (React-cached, read every request, so removing someone or retiring a firm takes effect at once) decides whether `/account` renders `TradeAccount` or `CustomerAccount`. Don't add a second sign-in, a trade cookie or a role column on `users` — and don't match by email domain (shared domains like gmail.com).
- **A trade checkout asks for the family and the firm's reference** (`parseTradeOrderDetails`, family required), saved by `setCheckoutDetails` with the firm onto `orders.trade_firm_id`/`family_name`/`customer_ref`; a non-trade checkout clears them. The trade view lists the account's orders by those (`TradeOrdersTable`: All / In progress / Delivered, search by family, reference or order number). The admin order page and the customer's order page show them.
- **A firm's trade discount is applied in one place: `getPricingData` (`pricing.server.ts`)**, which returns the list prices less the signed-in trade customer's `trade_firms.discount_percent` (`withTradeDiscount`, pure: every page-count rate scaled, so `getQuote`'s single rounding stays the only one; delivery is never discounted). Because every customer price is drawn from that table — the buy box, the price table, "from £X", the basket, the Stripe charge — they can't disagree, and a new page that shows a price gets it for free. Admin pages read `getListPricingData`. Never discount a quote, a line or a total anywhere else. `TradePriceNote` tells the customer; `orders.trade_discount_percent` freezes it at the pay click (Thintent gets the discounted line totals plus a "Trade price" spec row — it has no discount field).
- **On account: order now, Thintent invoices on net terms.** A firm an admin switched `on_account` (which needs `payment_terms_days`) gets "How to pay: On account / Pay now by card" at checkout (`resolvePayWith`). On account posts to `POST /api/checkout/account` — its own route because it runs the post-order side effects (Chromium, mail) in `after()`, so it is in `CHROMIUM_ROUTES` and the card route stays free of them; both share `freezeCheckout` (`checkout.server.ts`). Before placing, the route expires every Checkout Session still open for the order (`closeOpenCheckoutSessions` — an earlier "Pay now by card" could otherwise be paid too); a card payment that lands on an account order anyway is logged as a `card_paid_on_account` event for staff to refund. `placeOrderOnAccount` moves the draft to `awaiting_print` unpaid (`payment_method = 'account'`, `paid_at` null), freezing the terms and the firm's `accounts_email` onto the order. `pushOrderToThintent` sends `account: { creditDays, company, accountsEmail }` instead of `payment`; Thintent bills the firm on net terms and emails the invoice, which can be paid online there. Its answer's `invoice`, and later signed `invoice.updated` webhooks (`applyThintentInvoiceEvent`, applied only when newer), keep `orders.invoice_*` current; the first "paid" sets `paid_at`, which is what takings count. **`paid_at` no longer means "placed"** — the Thintent resend sweep, the Today page's settle wait and Thintent's reopen check read `placed_at`; "refund needed?" stays on `paid_at` and is card-only (an account order's invoice is voided or credited in Thintent). The trade view shows the balance and an Invoices panel (`accountBalance`, `invoiceStatusText`), and the order emails say "on account", never "paid".
- **No proofs on either view.** The mockups' "Your proof is ready" / "Proofs to approve" are the customer proof loop this site removed (see **Orders & Checkout**); the lead order card's tracker is Ordered → Printing → On its way → Delivered (`accountOrders.ts`).
- **Not built: a credit limit**, or firm-wide order lists (each person sees their own orders).
- **Applications become accounts in `/admin/trade`.** Pending ones are listed first (oldest first; the sidebar badge and a Today notice count them). **Approve** creates a new firm (named from the business, terms set there) or picks an existing active one, adds the applicant as its person, and moves the application `pending → approved` — one transaction, the move conditional on it still being pending, so two admins can't both approve. It then emails the applicant `tradeAccountReadyEmail`, which links to `/account?email=…` (the sign-in page, `accountSignInPageUrl`) — never a sign-in link, for the admin-invitation reason. Without email the page shows that link to pass on. **Decline** sends nothing (a refusal is better by phone) and takes a staff-only note. Decisions are final; an address already on another firm is refused at approval rather than moved. The application row is a snapshot of what was sent — editing the firm later doesn't change it.

## Photo Uploads

`POST /api/assets` returns a **presigned PUT**; the browser uploads bytes straight to object storage. Bytes must never pass through a Route Handler — Vercel caps serverless request bodies at 4.5MB and print-resolution photos exceed it. `src/lib/storage.ts` is written against the plain S3 API so AWS S3, Cloudflare R2 and MinIO all work (set `S3_ENDPOINT` for the latter two); the bucket needs a CORS rule permitting `PUT` from the site origin. Uploads are capped at `MAX_UPLOAD_BYTES` and restricted to `ALLOWED_IMAGE_TYPES`. With no `S3_*` env vars set the route returns 503 and the rest of the editor still works.

## Orders & Checkout

The basket → Stripe Checkout → order pipeline. `src/lib/orders.ts` holds the pure domain (status machine, VAT, totals, strict selection resolution, order numbers, Stripe line items — all unit-tested); `src/lib/orders.server.ts` is the owner-scoped seam (same `Owner`/404-not-403/slug-only discipline as `designs.server.ts`); `src/lib/adminOrders.server.ts` is the admin seam; `src/lib/orderFulfilment.server.ts` runs the post-payment side effects.

- **The basket is the owner's newest `orders` row with `status = 'draft'`**, one `order_items` line per design (adding a design twice returns the existing line). The order number (`TFS-<year>-<6 random digits>`, `makeOrderNumber`) is minted when the draft is created and retried on collision — random rather than sequential on purpose (no counter table, no order-volume leak; abandoned baskets burning numbers is harmless).
- **Axis ownership.** `pages` and `paper` are the *design's* spec and are copied into the line from the live design — never editable in the basket. `quantity` (copies), `delivery` and `size` (print size, see **Product Formats**) are the only per-line choices — none touches the artwork (`PATCH /api/cart/items/[itemId]`); `PATCH /api/cart` carries only checkout details. **Delivery is per line, not per order** — delivery options are product-scoped and a line is its own print job, which is what lets a basket mix products. Each line snapshots `delivery_option_id`/`delivery_label`/`delivery_price_pence`; `orders.delivery_pence` is their sum, and the order row has no delivery option of its own. A new line starts on the delivery already chosen for another line of the same product, else the product's default.
- **Pricing is always server-side and always strict.** The client sends slugs, never prices. Stored slugs are priced with `resolveSelectionStrict`, **never `getQuote` directly** — `getQuote`'s `find()` silently falls back to the first option for an unknown id, which is fine for the live configurator and wrong for a slug whose option has since been deactivated. A line whose option no longer prices is reported as `stale` (and a soft-deleted design as `designMissing`); the basket shows the problem and checkout refuses (`Cart.ready`).
- **Snapshots freeze at the pay click, not at add.** `order_items.doc_snapshot`/`quote_snapshot` are NOT NULL, so they're written at add time as placeholders and rewritten wholesale by `prepareOrderForPayment` (inside one transaction, together with the order totals and `vat_rate`). Basket display always reads the live design. After payment the snapshots are history — nothing rewrites them. That includes `format_snapshot` (the product's `ProductFormat` at the pay click): order pages and emails write the spec line from it, because a format's labels stay editable; only lines paid before it existed fall back to the live format. The admin order page's "artwork drawn at" reads `docTrim(doc_snapshot)`.
- **Money:** `line_total_pence = unit_price_pence × copies`, `subtotal = Σ line totals`, `total = subtotal + Σ line delivery`; prices are VAT-inclusive so `vat_pence` is backed *out*: each product has a VAT treatment (`products.vat_treatment` — standard 20% / reduced 5% / zero-rated / exempt, set in `/admin/products`, default standard; `src/lib/vat.ts`), frozen onto `order_items.vat_treatment` at the pay click, and `computeOrderTotals` backs VAT out of what was charged at each treatment, a line's delivery taxed with its product. A null line treatment is a pre-treatment line, charged standard. Customer copy says "No VAT", never "VAT of £0.00" (`vatIncludedText`/`priceVatNote`). `buildStripeLineItems` produces one Stripe line per order line (unit × copies) followed by that line's delivery line when it costs anything, so Stripe's sum equals `total_pence` by construction — `createCheckoutSessionForOrder` asserts it.
- **`finaliseOrder` is one atomic conditional UPDATE** (`… WHERE id = ? AND status = 'draft'`), shared by the Stripe webhook (`POST /api/stripe/webhook`) and the customer's return redirect (`GET /api/checkout/return` — a Route Handler, not the page, because finalising is a side effect). The two can race; only the one that flips the row writes the `placed` event, marks the designs `ordered` and schedules side effects. Both find the order via `session.metadata.orderId` (not the stored session id — a double-clicked Pay creates two sessions for one order) and require `payment_status === 'paid'`. Because the return route finalises too, **local dev works without webhook forwarding**; keep the webhook configured in production so a closed tab can't lose a paid order. A webhook naming an unknown order is answered 200 + logged, never 4xx (Stripe would retry forever).
- **Side effects are best-effort, inside `after()`.** `runPostPaymentSideEffects` renders a proof per line from `doc_snapshot` (`renderProofPdf`, the same `/proof-render` screenshot path as `/api/proof`) → S3 `orders/<orderNumber>/<itemId>-v<n>.pdf` → `order_proofs`, then sends the customer confirmation and the `ORDER_NOTIFY_EMAIL` copy via Resend. Each failure becomes an `order_events` row (`proof_failed`/`email_failed`) + `console.error`; none ever fails the order. Both are silent no-ops when `S3_*` / `RESEND_*` aren't configured. `orderFulfilment.server.ts` is the **only** orders module allowed to import Chromium or the mail client — keep the basket/checkout routes free of them.
- **Emails share one branded shell** (`brandedEmailHtml` and its pieces in `orderEmails.ts`: tables + inline styles, the site's palette, a preheader). The logo is an **inline `cid:` attachment** (`emailLogo.ts`, a small PNG embedded as base64), never an image linked from the site — Gmail can't fetch `localhost` or a preview deploy, Outlook won't show WebP, and a linked image waits behind "show images". A new email builds on the shell and returns `brandedAttachments()`.
- **Status machine:** `ORDER_STATUS_TRANSITIONS` in `orders.ts` is the only path between statuses — `draft → awaiting_print → in_production → shipped → delivered`. `draft → awaiting_print` happens solely through payment; admin moves go through `adminUpdateOrderStatus` (conditional on the status the admin was looking at, writes a `status_changed` event).
- **Refunds are made in Stripe and mirrored here, never made here.** `order_refunds` is written only by `syncStripeRefunds` (`src/lib/refunds.server.ts`), from the Stripe webhook's `refund.created`/`refund.updated`/`refund.failed` (and `charge.refunded`): each event re-reads *every* refund on the payment (`listPaymentRefunds`) and upserts them by `stripe_refund_id`, so delivery order doesn't matter, and a status change is claimed with a conditional write so only one delivery records the `refund_recorded`/`refund_failed` event. Only `succeeded` refunds count (`refundedPence`, pure). `refundStatusEffect` decides what a full refund does: a cancelled or delivered order moves to `refunded` by itself (`settleRefundedStatus`, also run after Thintent moves an order, since a refund made before the cancel settles when it arrives); one still awaiting print/in production is **not** stopped — status changes in Thintent — so it gets a "refunded, but still going to print" notice instead; part refunds change no status. The customer's order page shows succeeded refunds as "Refunded to your card"; admin lists every refund with its status. There is no Refund button: the dashboard is the way in, and the webhook is the only path in, so it must subscribe to the refund events.
- **There is no customer proof loop, and don't reintroduce one.** The design is checked *before* it can be paid for (see **Pre-Order Checks**), so a paid order is simply waiting to reach the press — `awaiting_print` means "paid, not yet sent to press". A proof is a **press artefact and admin-only in full**: `order_proofs`/`order_proof_pages` carry the rendered artwork and the on-demand print PDF, admins view and regenerate them (`POST /api/admin/orders/[id]/items/[itemId]/proof`), and nothing on the customer path reads them. `order_proofs` therefore has no `status`/`sent_at`/`responded_at`/`customer_note`, `orders` has no `share_token`, and there is no `/proof/[token]` share page, no `proofReadyEmail` and no approve/request-changes route. A test in `orders.test.ts` asserts the removed statuses stay gone.
- **Cookies:** `GET /api/cart` (the header badge, every page) uses `readOwner()` and must never mint a guest cookie; only mutations use `getOrCreateOwner()`. The return route deliberately does **not** re-issue a guest cookie from the session — a leaked return URL would otherwise claim another visitor's designs. `deleteDesign` also drops that design's lines from draft orders (done in `designs.server.ts` to avoid an import cycle).
- Env: `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `RESEND_API_KEY`, `EMAIL_FROM`, `ORDER_NOTIFY_EMAIL`, and for **Thintent Sync** `THINTENT_API_URL`, `THINTENT_API_KEY`, `THINTENT_WEBHOOK_SECRET`, `CRON_SECRET` — see `.env.example`, including the `stripe listen --forward-to localhost:3000/api/stripe/webhook` dev setup. Unset Stripe → `POST /api/checkout` 503s and the checkout page says so; the basket still works.
- **The design page's selection is carried as query params** (`?quantity=&pages=&paper=&delivery=`, built by `selectionSearchParams`) from `/products/[slug]/[template]` → `/design` → "Add to basket". `/design` validates them against the product's pricing with `parseCarriedSelection` (unknown slugs drop to the default). `pages`/`paper` seed only a *new* design (a saved one owns them, and the editor strips them from the URL once a design id exists); `quantity`/`delivery` stay in the URL and are sent with `POST /api/cart/items`, and remain editable in the basket.

## Review Requests

One email per completed order asks the family how we did, linking to the Google review page (`GOOGLE_REVIEWS.writeReviewUrl`). `src/lib/reviewRequest.ts` is pure and tested; `src/lib/reviewRequests.server.ts` is the seam; `GET /api/cron/review-requests` (weekday mornings, `vercel.json`, Bearer `CRON_SECRET`) sends what is due.

- **Timing is funeral-sector practice, not shop practice:** 14 days after the funeral date given at checkout (the latest on the order), or 21 days after the order is marked delivered/completed when there is none — never before completion. A request stays sendable for 14 days after it falls due and is then dropped, so a missed run or a long-completed order never produces a late email. Only one is ever sent per order: `orders.review_requested_at` is claimed with a conditional UPDATE before sending and released if the send fails.
- **Never sent to:** an order that isn't `delivered`, one with any succeeded refund, an address in `review_request_opt_outs`, or an order whose `review_request_opt_out` isn't explicitly `false`. That column is set from the checkout form's "Email me once after the funeral to ask how we did" box — **pre-ticked**, so unticking it is the refusal (a pre-ticked box isn't valid consent, but the soft opt-in needs only a simple chance to refuse) — and is **null until checkout asks** — so orders from before the question existed, and a checkout form from an older tab, are never sent one. This is the soft opt-in: the chance to refuse at collection and in every message.
- **Unsubscribing:** the email carries a link to `/email/unsubscribe?t=…` (an HMAC of the lowercased address keyed off `AUTH_SECRET`, `reviewOptOutToken`; no expiry, no table of tokens). Opening the page changes nothing — mail scanners open every link — its button posts to `POST /api/email/unsubscribe`, which mail clients' own button (RFC 8058 `List-Unsubscribe`/`List-Unsubscribe-Post` headers) also posts to directly. The opt-out is per address, so it holds for the next order too. Without `AUTH_SECRET` or Resend nothing is sent.
- **Wording** (`reviewRequestEmail` in `orderEmails.ts`) is for someone grieving: thanks first, one ask framed as helping other families, "if you feel comfortable", no obligation, never "five stars". Keep it that way.

## Pre-Order Checks

Mistakes are caught **before** money changes hands, at the add-to-basket click, while the customer is still in front of the editor and can fix them in a click — not afterwards by staff reviewing a rendered proof.

- **`src/lib/designReadiness.ts` is pure and unit-tested** (same discipline as `orders.ts`/`seedData.ts`). `checkDesignReadiness(doc, templatePages)` returns `{ blocking, warnings }`. Two kinds of mistake, treated very differently:
  - **Empty photo window → blocking.** `ImageElement.src === null` is unprintable: the editor's dashed "Double-click to add a photo" box is real ink on the press PDF. This is the fix for that bug, at source — you can't order one.
  - **Text still identical to the template's placeholder → warning.** Suspicious but legitimate ("In loving memory" is what many customers actually want), so warn, make them look, and record that they did.
  - **Only `TextElement.placeholder` text warns.** Fixed wording ("Order of Service", a motto) is meant to stay, and flagging it buries the warning that matters under noise the customer learns to click through. The flag is set by the authoring editor's toolbar toggle, `makeStarterDoc` and the generator's `text` helper (name, dates, service, interior placeholder — not the farewell/thanks). A layout with **no** flags at all predates the flag and falls back to warning on every text run, until an admin marks it up.
- **Compared per page role, not per element id.** `instantiateLayout` freshens every id, so the check compares normalised text (whitespace/case-insensitive) against the template page the design page came from — cover→cover, last→back, interiors→the one authored middle page. Wording *moved* to another page is plainly a deliberate edit and doesn't warn. Repeated interior hits collapse into one issue with an `occurrences` count, so an untouched 24-page booklet reports one row, not a dozen.
- **A `locked` element is never the customer's blocker** — it's template artwork they can't touch.
- **Enforced server-side in `addCartItem`**, via `src/lib/designReadiness.server.ts` (the seam that resolves the template's `layout`, or `makeStarterDoc` when it has none). The client runs nothing the server trusts: it sends `acknowledgeDefaults`, never a verdict. Blocking → 409 `{ reason: "blocked", readiness }`; unconfirmed warnings → 409 `{ reason: "confirm", readiness }`, both carried through `CartError.details`. `PreOrderCheckDialog` renders either and re-POSTs with the acknowledgement. An archived template can't be loaded for comparison, so warnings are skipped and only the blocking check runs — the right way round.
- **The confirmation is persisted for audit**: `order_items.defaults_ack` (the exact warnings shown) + `defaults_ack_at`. A snapshot like the spec columns beside it, and for the same reason — it is the evidence for "you approved this wording", so a later edit to the design must never rewrite it. Null means nothing was warned about, **not** that the check was skipped. Re-adding an already-present design is idempotent and doesn't re-run the gate.


## Upload Your Own Design

`/upload` prints the customer's **own** artwork — a print PDF, or a link to a Canva design — on any sellable product, in four steps (`UploadFlow.tsx`, built from the redesign mockups): what you're printing (product, pages, paper, copies — the product's own pricing axes), your design, check and preview, confirm. It wears the slim `TaskHeader`/`TaskFooter`, not the shop chrome.

- **`artwork_uploads` is the counterpart of `designs`** for a line the editor never touched: owner-scoped (user_id / guest_token, claimed on sign-in like designs, and with the paid orders claimed by email), immutable — a different file is a new row. It is deliberately **not** tied to a product or page count: the customer can go back to step 1 after uploading.
- **Bytes never pass through a Route Handler.** `POST /api/uploads` (`source: "pdf"`) reserves a row and returns a presigned PUT to `uploads/incoming/<id>.pdf`, exactly like photos; `source: "canva"` just records a validated link (`parseCanvaUrl`). `MAX_ARTWORK_BYTES` is 50MB, enforced again when the server reads the object (`readObject(key, maxBytes)`), since a presigned PUT doesn't bind the size.
- **The file printed is the file checked.** The presigned PUT stays usable after the check, so `analyseUpload` writes the bytes it analysed to a fresh server-only key (`uploads/<id>-<random>.pdf`) and moves the row's `storage_key`/`url` there in the same conditional UPDATE that stores the facts (`WHERE analysis IS NULL` — of two racing checks the first wins). Only that frozen copy ever reaches an order line or the admin page. Keys carry no owner: a guest's owner key is their session cookie, and press-file links get handed on.
- **Facts and verdict are separate.** `src/lib/pdfAnalysis.ts` (pure, pdf-lib only, tested with generated PDFs) reads the file once — page boxes and bleed, each sizeable image's resolution at the size its content stream draws it (a small tokenizer walks q/Q/cm/Do into form XObjects), and fonts that draw visible text without being embedded — and `uploads.server.ts` stores it as `artwork_uploads.analysis`. `evaluateArtwork` (`src/lib/artwork.ts`, pure, tested) turns those facts into the checks shown, against the current choice. Re-checking another product or page count never re-reads the file.
- **Same block/warn split as the pre-order check.** Wrong size, the wrong way round, spreads, the wrong page count, an unreadable file → blocking ("Upload a different file"; a page-count mismatch we also sell offers "Switch to N pages"). No bleed, scaled to fit, soft photos (< `MIN_PRINT_PPI` at the *printed* size — a board's A size, via `printTrim`), missing fonts, a one-page file for a two-sided card → warnings, accepted with "Print it as it is". Equal margins all round with no TrimBox read as bleed (or bleed + crop marks, Canva's "PDF Print"). A board takes any A-shaped file.
- **The server re-runs the check at add time** (`addUploadCartItem`, `POST /api/cart/uploads`): blocking → 409 `reason: "blocked"`, unaccepted warnings → 409 `reason: "confirm"`, both carrying the `report`; the "I've checked the names, dates and spelling" tick (`confirmed`) is required. The client sends choices — including the delivery the confirm step totalled — never a verdict. Adding an upload already in the basket **updates** its line to the choice just checked, unlike a design's idempotent re-add. A page the analysis couldn't walk to the end (undecodable content, or past the operator ceiling) is listed in `uncheckedPages` and warns ("We couldn't check every page") instead of passing photos and fonts.
- **The pay click re-checks the options an upload was checked against**: if its page-count option's page count or (for a board) print size changed since it was added, `prepareOrderForPayment` refuses the line — the design path's "needs re-saving" equivalent. A board's print size is read from the option's label or slug (`printTrim` looks for an A size anywhere in either).
- **An order line is a design *or* an upload** (`order_items.design_id` / `upload_id`; `template_id` and `doc_snapshot` are null on an upload line). `artwork_snapshot` freezes the file, its page count, the trim, the checks shown, when warnings were accepted and when the wording was confirmed — written once at add time, since an upload never changes; nothing rewrites it. `service_date` is the optional funeral date from the confirm step. The checkout form asks again, prefilled with the earliest date in the basket, and writes its answer onto **every** line, design and upload alike (`setCheckoutDetails`), because a basket is one family's order for one service. It becomes Thintent's due date and drives the admin "Today" page. In the basket only copies and delivery are editable, as for designs.
- **The customer's PDF is the press file.** Fulfilment renders no proof for an upload line, and the admin order page links the PDF (or the Canva link, with a note that it is unchecked) and lists the warnings the customer accepted. A Canva link is checked by staff when they download it.
- **The preview is drawn in the browser** by pdf.js (`pdfjs-dist`, legacy build — the modern one needs browsers newer than many customers have), loaded on first use (`src/lib/pdfPreview.ts`) with its worker started from `src/lib/pdfWorker.ts` via `new Worker(new URL(…, import.meta.url))`. It reads the chosen `File`, never the stored copy, and decides nothing — the server's report is the only verdict. `previewGroups` lays pages out as they're held: a booklet's front, openings, back; a card's front and back.

## Thintent Sync

The print shop runs its work in **Thintent**, so every paid order is also sent there as a confirmed, already-paid job — the shop manages it from one place, and this site still emails and keeps its own record. `src/lib/thintent.ts` is pure and tested (the payload, the status mapping, the signature check); `src/lib/thintent.server.ts` is the seam.

- **Out: one POST per paid order.** `runPostPaymentSideEffects` calls `pushOrderToThintent` after the proofs (so the job links their page images) and after the emails (an email is never retried; the push is). It posts `buildThintentOrderPayload(loadOrderDetail(...))` to Thintent's `POST /api/v1/orders` (Bearer `THINTENT_API_KEY`): VAT-inclusive pence that must add up (lines = subtotal, delivery = Σ line delivery, payment = total, or Thintent 422s), each line's `vatTreatment` and the delivery's (the line deliveries are grouped by treatment: the largest group is Thintent's one delivery charge, any other goes over as a "Delivery — … (zero-rated items)" line at its own treatment — `splitDeliveryCharges`), artwork as **links** (the upload's PDF, the Canva link, a design's newest proof pages plus the admin order page where the print PDF is made), `service_date` as the job's due date, `test` for a test-mode Stripe key. The job number and URL land on `orders.thintent_job_ref`/`thintent_job_url`.
- **Best-effort and retried, never lost.** A failure is a `thintent_failed` event (a repeat of the same refusal doesn't add another row), never a failed order. `GET /api/cron/thintent-sync` (hourly, `vercel.json`, Bearer `CRON_SECRET`) re-sends the past week's paid orders with no job ref — leaving those paid in the last 10 minutes to fulfilment's own send, since a repeat only returns the job already made and one sent before its proofs would link "no proof yet" for good — and the admin order page has "Send to Thintent". Only an `awaiting_print` order is ever sent (`canSendToThintent`): one an admin moved on by hand is being handled outside Thintent, and sending it would make a second job. Re-sending is safe: Thintent keys the job on the order number and answers a repeat with the job it made.
- **Back: signed `job.updated` webhooks** to `POST /api/thintent/webhook`, verified with `THINTENT_WEBHOOK_SECRET` (`Thintent-Signature: t=…,v1=<hmac-sha256 of "t.body">`, 5-minute tolerance). The body is the job's full state, so delivery order doesn't matter. `thintentStatusMoves` (pure) decides the moves, each made through `moveOrderStatus` (shared with the admin status form) with actor `thintent`: forward through `ORDER_STATUS_TRANSITIONS` (in_production/ready_for_dispatch → in_production, dispatched → shipped, completed → delivered); **a cancel cancels** an order that hasn't shipped (a shipped/delivered one stays as it is and gets a `thintent_cancelled` event for staff); and a job reopened in Thintent reopens the order (cancelled → awaiting_print, then forward) **only if Thintent made the cancel** — that step is deliberately absent from `ORDER_STATUS_TRANSITIONS`, so no admin form offers it, and a cancel made here stays. Courier and tracking go on the order and show on `/orders/[id]`. Unknown orders are answered 200 + logged, like the Stripe webhook.
- **A cancel never moves money.** The delivery whose conditional move actually cancelled the order emails the customer ("won't be printed; a refund, if due, goes back to your card") and `ORDER_NOTIFY_EMAIL` ("nothing has been refunded") via `sendOrderCancelledEmails`; the admin order page shows "Refund needed?" on a paid cancelled order until it's refunded in full. Thintent's own model agrees: a website (`online_store`) payment can't be reverted there — the refund is made in this site's Stripe.
- **Refunds go across as credit notes.** Each succeeded `order_refunds` row is POSTed to Thintent's `/api/v1/orders/{orderNumber}/refunds` (`pushOrderRefundsToThintent`, payload `buildThintentRefundPayload`), where it becomes a credit note born refunded by `online_store` — Thintent moves no money and emails nobody, and its ledger takes it out of the bank, where the website payment went in. `order_refunds.thintent_credit_ref` (`CN-<n>`) marks it sent. Sent by the Stripe webhook delivery that saw the refund succeed, by `pushOrderToThintent` once a job exists (a refund made earlier had nothing to attach to), by the hourly cron (refunds older than 10 minutes, so it doesn't race the webhook's send; a week of retries), and by the admin "Send refunds to Thintent" button. It needs only the job ref, not a sendable status — refunds are what happen to cancelled orders. Thintent keys the credit note on the Stripe refund id, so a resend is safe.
- **Status has one writer per order.** Once an order has a `thintent_job_ref`, `adminUpdateOrderStatus` refuses a move (409) and `AdminOrderStatusForm` says the status is managed in Thintent — a move here would never reach Thintent, and nothing here pushes status there (that would loop). The form stays as the override for an order that never got there, and its route runs `settleRefundedStatus` after a move, like the webhooks. Thintent's webhooks and `settleRefundedStatus` move it through `moveOrderStatus` directly.
- Unset `THINTENT_API_URL`/`THINTENT_API_KEY` → nothing is sent; unset `THINTENT_WEBHOOK_SECRET` → the webhook 503s.

## Site Subscription

The business pays a monthly subscription (£120, a Stripe Price) to keep the online shop open, modelled on Thintent's own billing. While it is unpaid, customers can browse products, designs and prices but can't design, upload or buy; orders already paid for carry on (webhooks, fulfilment, Thintent sync, refunds and the customer's order pages are never gated), and the contact form stays open.

- **The switch is `SUBSCRIPTION_REQUIRED=1`.** Unset, nothing is gated and `isShopOpen()` doesn't even read the table; the subscription can still be taken out and shows in `/admin/billing`. It's the developer's switch, in Vercel — never an admin setting.
- **Its own Stripe account.** `BILLING_STRIPE_SECRET_KEY` / `BILLING_STRIPE_PRICE_ID` / `BILLING_STRIPE_WEBHOOK_SECRET`, deliberately separate from the `STRIPE_*` keys customers pay orders through: the subscription is billed on the developer's account (shared with Thintent's shop subscriptions), while the shop's checkout moves to the business's own account. So `POST /api/billing/webhook` acts only on this site's stored customer and answers 200 to anyone else's; subscribe it to `checkout.session.completed`, `customer.subscription.*` and `invoice.paid`/`payment_failed`/`voided`/`marked_uncollectible` (paying the older of two open invoices moves the grace clock without changing the subscription's status). Syncs run one at a time under a row lock, so two events landing together can't store the older state last; `/admin/billing` re-syncs on every visit, and Subscribe asks Stripe before starting a Checkout (refusing a second subscription, expiring any earlier open Checkout).
- **`src/lib/siteAccess.ts` is pure and tested** — the rule: `active`/`trialing` and `past_due` (grace while Stripe retries the card) open, but a failed payment only for `PAST_DUE_GRACE_DAYS` (14) from the **oldest** unpaid invoice (`site_billing.past_due_since`, read from Stripe on every sync) — then `overdue`, closed, whatever Stripe still calls it. What Stripe does when its retries run out is a dashboard setting, and "leave the subscription past-due" must not keep an unpaid shop open for good; the oldest invoice, so next month's renewal can't restart the clock. An overdue subscription is settled in the portal — `/admin/billing` doesn't offer a second subscription; a portal cancellation (`cancel_at_period_end` or `cancel_at`) stays open until its date and closes on it by the clock, without waiting for the `deleted` event; everything else, including any status Stripe adds later, closes. Unlike Thintent, a subscription Stripe has *ended* closes at once whatever period end it last reported. `pickSubscription` chooses which of the customer's subscriptions counts (a good one over a newer ended one), so a re-subscribe isn't undone by the old one's late events.
- **`site_billing` is a one-row table** (id 1), written only by `syncSiteSubscription` (`siteBilling.server.ts`), which re-reads the customer's subscriptions from Stripe — from the webhook and from `/api/admin/billing/return`, where Checkout and the billing portal send the admin back (so it works locally without a webhook). The billing customer is created and stored before Checkout starts.
- **Enforced server-side** by `if (!(await isShopOpen())) return shopClosedResponse();` (503, `reason: "shop-closed"`) on the first line of every customer write: design save (`POST`/`PATCH /api/designs`), `POST /api/uploads` and its check, `POST /api/assets` (admins exempt — template previews use it), the basket (`POST /api/cart/items`, `PATCH /api/cart/items/[itemId]`, `POST /api/cart/uploads`, `PATCH /api/cart`) and `POST /api/checkout`. Deletes and reads stay open. A new customer write route gets the same line. The pages follow: `/design` and `/upload` show `ShopClosedNotice`, `/cart` shows it above the basket (still readable and removable, its choices and checkout switched off), `/checkout` redirects to the basket, the design page's buy box offers the phone, and the header strip says the shop isn't taking orders online.
- `/admin/billing` subscribes (Checkout) and manages (Stripe's billing portal) by plain form posts; every admin page carries `billingNotice` when the shop is closed, a payment failed or a cancellation is running out.

## Admin Area

`/admin` manages the catalogue: products (label, card blurb, shop group, sort, active) + their five pricing tables (`/admin/products/[slug]`), template categories, template metadata, and visual template-layout authoring (`/admin/templates/[slug]/layout` mounts `DesignEditor` in `templateAuthoring` mode — saves PUT `templates.draft_layout` instead of `/api/designs`; it sits outside the `(protected)` route group because the editor is full-bleed, and calls `requireAdmin()` itself).

- **Admins sign in by emailed link, against an `admins` table — no password, no provider.** `/admin/login` takes an email; only an address listed in `admins` is sent a link (the response is identical either way, and the route is rate-limited per IP). The link is a `login_tokens` row with `purpose = 'admin'`, and it opens `/admin/verify`, a page that spends nothing on GET: its form (`AdminVerifyForm`) POSTs the token to `/api/admin/verify` by script as soon as it mounts, with a button as the no-script fallback — mail scanners fetch every link in an email but don't run the page, and would otherwise burn the single-use token on the only way into `/admin`. Don't turn the link itself into the sign-in. That route spends only admin tokens (and customer links are spent only by `/api/auth/verify` — each reads just its own purpose), re-checks the address is still an admin at the click and sets the `tfs_admin` cookie: stateless HMAC like `tfs_user` (both are `signedSession`s, `src/lib/signedSession.ts`), keyed off `AUTH_SECRET` with its own derivation, 12h. The admin cookie **never** uses the customer cookie's public development secret — the owner's id is fixed in the migration, so that would let anyone forge an owner cookie on a dev server reachable from outside; without `AUTH_SECRET`, development signs it with a random per-process secret instead. The login route makes and sends the link inside `after()`, so an admin's address answers exactly as fast as a stranger's. `src/lib/adminSession.ts` is the cookie, `src/lib/adminAuth.server.ts` the seam: `getCurrentAdmin()` reads the `admins` row behind the cookie on every request, so removing someone signs them out at once. The `(protected)` layout's `requireAdmin()` is UX; the security boundary is the `isAdmin()` check on the first line of **every** `/api/admin/*` handler. `/admin/access` lists admins, grants access (`POST /api/admin/access` — emails an invitation that links to the sign-in page with the address filled in, never a sign-in link, since an invitation can sit unread for days) and removes it (`DELETE /api/admin/access/[id]`). **The owner row (`is_owner`, inserted by migration `0023_admins`) can never be removed**, and nobody removes themselves (`removeAdminRefusal`, pure + tested in `adminAccess.ts`); the delete's WHERE carries the owner guard too. `ADMIN_PASSWORD`/`ADMIN_SESSION_SECRET` are gone. In production admin sign-in needs `AUTH_SECRET` and Resend, exactly like customer accounts; in development a missing Resend prints the link in the server's terminal — never on screen, unlike a customer's.
- **`src/lib/adminCatalogue.server.ts` is the admin seam** — same slug-only discipline as `designs.server.ts`, but unfiltered by active/status. A `kind → table` map keeps the five pricing tables on one code path (`OptionKind`: `paper`/`quantity`/`page-count`/`delivery`/`size`).
- **Slugs are immutable after create** (they're snapshot keys in order history and appear in URLs) — admin forms render them read-only; no update touches a slug column. **Retire, don't delete**: `is_active = false` or `status = 'archived'` (designs FK-restrict into everything anyway). The **one** exception is `DELETE /api/admin/templates/[slug]` → `adminDeleteTemplate`, for a template *nothing has ever used* — a `templates:generate` reject would otherwise be an archived row forever. It counts `designs` rows first (soft-deleted included — `deleted_at` leaves the row and its FK) and 409s with "archive it instead" if any exist, which transitively protects order history too, since a template only reaches an order through a design; `isRowReferencedError` (`src/db/errors.ts`) catches the create-vs-delete race. Don't generalise this to the pricing tables — their rows are always referenced by live orders.
- **Admins can edit a customer's design on their behalf** — for a customer who is stuck. `/admin/designs` lists designs and searches a pasted editor link (straight to it), an account's email, or the wording on a design (its text elements' `text`, via `json_extract` — not the doc's keys or image URLs — so a guest's design is found by the name of the person it's for); a customer's page lists theirs (an account's, plus, for a guest, the designs on their paid orders — not everything made in that browser, which may be a shared office computer). `/admin/designs/[id]` (outside `(protected)`, full-bleed, `requireAdmin()` itself) mounts `DesignEditor` with `adminEditing`: it saves `PATCH /api/admin/designs/[id]` onto the **customer's own row**, with the same checks and revision guard as theirs, and hides the basket and share link; a photo an admin adds is filed under the design's owner (`/api/assets` → `adminDesignOwner`). It is the only path past the owner scope — `adminFindDesign`/`adminWriteDesign` in `designs.server.ts`, called only from `adminDesigns.server.ts` and the `/api/admin/designs` route. Editing an ordered design changes no paid order (they print from `doc_snapshot`); the editor's banner says so, and the admin order page's "edit design" link opens it here.
- **`/admin` is the "Today" page**, and every admin page has the plum sidebar (`AdminNav.tsx`; its Orders badge is paid-not-yet-sent). The rules are pure and tested in `src/lib/adminDashboard.ts`: dates are the shop's **Europe/London** day (`shopDate`/`shopDayStart` — Vercel runs in UTC), "must go out today" is an open order whose service date is on or before the next weekday (bank holidays aren't known), the cut-off countdown reads `ORDER_CUTOFF`, and `actionItems` gives each order at most one "needs you" row. In order: an unrefunded paid cancel; a missing proof (only when storage is configured, since without it nothing renders); a missing Thintent job, both after 10 minutes; then, only while the order is still awaiting print, a Canva link or accepted upload warnings; then an urgent print. Takings are cash-basis — a payment on the day it was paid, a refund on the day it was made, VAT-inclusive; the average order is before refunds. A customer's "spent" is less refunds. Orders with no funeral date never reach "must go out today", because the date is optional. `adminDashboard.server.ts` gathers the facts read-only. There is no proof-sent/approval stage on this page, for the reason in **Orders & Checkout**.
- **A customer is an email, not a table** (`src/lib/adminCustomers.ts`, pure + tested). It is the account's email when the order was placed signed in, otherwise the contact email typed at checkout, lowercased. Accounts with no orders are listed too. `/admin/customers` groups in memory (the order book is small) and searches name/email/phone/postcode/order number; `/admin/customers/[email]` is read-only. The orders list searches the same fields in SQL (`likeContains` escapes `%`/`_`).
- **Field validation is pure and tested** — `src/lib/adminValidation.ts` (slug/pence/multiplier-4dp/page-count/hex/layout-pages parsers) and `src/lib/money.ts` (`poundsToPence` — admins type pounds, the wire and DB carry pence; malformed input is rejected, never rounded).
- Template preview uploads reuse the `/api/assets` presign flow; `next.config.ts` derives the storage host for `images.remotePatterns` from the `S3_*` env vars — without that, `next/image` hard-errors on uploaded previews.
- Draft/archived templates never leak: customer loaders filter `status = 'published'`, and the public `GET /api/templates/[slug]/layout` (used by the editor's apply-template fetch) 404s for them.
- **Two independent gates, don't conflate them.** `templates.status` governs whether the *template* is visible at all; `draft_layout` governs whether the latest *layout* edits are live. `PUT /api/admin/templates/[slug]/layout` saves the draft; `POST` takes `{ action: 'publish' | 'discard' | 'clear' }` (publish = draft→live, discard = drop the draft, clear = remove both and revert to `makeStarterDoc()`). `publish` 409s when there's no draft rather than silently no-opping. The editor's Publish button `persist()`s first so unflushed autosave edits are included.
- **Publishing auto-regenerates the preview thumbnail from page 1**, so an admin never has to screenshot/upload it by hand: `src/lib/templateThumbnail.server.ts` reuses the exact same `/proof-render` target `/api/proof` screenshots (screen resolution, one page, not print DPI), then `uploadObject` (a direct server-side S3 `PutObjectCommand` in `storage.ts` — deliberately not the presigned-PUT path used for browser uploads, since the server already holds these bytes) writes it and `adminUpdateTemplate` points `previewImageUrl` at it. This is best-effort: a screenshot/upload failure is caught and logged, never fails the publish itself, and silently no-ops when `S3_*` isn't configured. `launchHeadlessBrowser` (`src/lib/headlessBrowser.server.ts`) is shared between this and `/api/proof` — keep new Chromium call sites on that one helper.

## Bulk Template Generation

`npm run templates:generate` (`src/db/generateTemplates.ts`) turns curated specs into real catalogue rows, so a large template library doesn't have to be drawn by hand in the authoring editor.

- **Flat products have their own library, `src/lib/flatTemplates.ts`** (pure, tested): A6 cards and A-series boards *borrow a booklet cover* (and back page) and scale its type, so they stay in the booklet family; thank-you fronts, bookmarks and the board collage are its own compositions. Borrowed covers are paper, solid and spray archetypes only — the booklet's artwork covers place their background at A5's bleed. The **memorial set** (`MEMORIAL_SET`) is the exception: its own `card-*` fronts (landscape scene, flower band, stem, corner spray, butterflies/robin, branch) place the background at the product's own bleed (`backgroundElement(src, trim)`), and every entry also builds a `bookmark-*` twin of the same name so a family can order the pair — add to the set as a pair, never one half. The runner sends booklet specs to `--product` (refusing a product that isn't an A5 booklet) and each flat spec to its own product; with no `--product` both run.
- **`src/lib/templateGenerator.ts` is pure and DB-free** (same discipline as `seedData.ts`, and unit-tested the same way). It splits a template into an **archetype** — the composition (`framed`, `portrait`, `minimal`, `arch`, `corners`), which is what actually makes two templates look different — and a **style** (`TEMPLATE_PALETTES` x `TEMPLATE_TYPE_SETS` x a clipart motif) layered over it. `buildTemplateLayout` always returns exactly `TEMPLATE_PAGE_COUNT` pages, so its output satisfies `parseLayoutPages` and can go straight to `templates.layout`.
- **Curate combinations; don't take the cartesian product.** 5 archetypes x 6 palettes x 6 type sets x 12 motifs is >2000 permutations, and shipping all of them reads as machine-stamped. `TEMPLATE_SPECS` is a hand-picked list — add to it rather than generating combinations programmatically.
- **Generated templates are always created `status: "draft"`.** The layout is live on the row but the template stays invisible until a human reviews it and flips the status in `/admin/templates` — exactly what the status gate (independent of `draft_layout`, see **Admin Area**) exists for. The runner goes through the normal `adminSaveTemplateDraftLayout` → `adminPublishTemplateLayout` seam rather than writing `layout` directly, so rows end up in the same state the authoring editor would leave them: layout set, no dangling draft.
- **Thumbnails need a running server.** Rendering reuses `renderTemplateThumbnail` (the same `/proof-render` screenshot path as the admin publish flow), so start `npm run dev` first or pass `--origin`; `--no-thumbnails` skips it. Output goes to S3 when configured, else `public/templates/<slug>/cover.png`. Failures are best-effort and never abort the run.
- Flags: `--force` (rebuild existing slugs), `--only=slug,slug`, `--product=`, `--origin=`, `--no-thumbnails`. Without `--force` existing slugs are skipped, so re-running is safe.
- **The element vocabulary is the ceiling on how distinctive these can get.** `rect`/`circle` shapes take an optional `fill` (undefined = outline only, every older shape), a frame can have `corners: "notched"` and a photo `shape: "notched"` (both cut the same `NOTCH_RADIUS`, drawn as SVG at the box's own px size / a CSS mask), and clipart is lucide's icons plus the hand-drawn ornaments in `Ornaments.tsx` (dove, swash, scroll divider, scrolled frame — each with an `aspect` in `CLIPARTS`, so the editor adds it at its own shape). Clipart still has no flip, so mirrored corner ornaments need rotation or a symmetric drawing. Genuinely richer artwork (textures, watercolour florals) comes from **Background Artwork** below, not from new vector archetypes.
- **`src/lib/classicTemplates.ts` is the classic family** (pure, tested): the business's own twelve long-standing formal covers under their original names (Border Corners, Classic Posh, Order of Gold, Single Dove, Star, …) — line or notched borders, a pastel card, a deep burgundy ground, the gold scrolled cartouche — measured from the existing covers and rebuilt from the editor's vocabulary, so every part stays editable. A design is a cover plus `chrome` (border, ground panels, ornaments) that the interior and back pages repeat; a dark ground sets its interior on paper. Their wording placeholders (`SUNRISE_SUNSET`, `SERVICE_WHEN`, `VENUE`, …) are flagged with `field()`, fixed headings with `fixed()`. Each spec pins its preview `portrait` on create, since a cover with no artwork would otherwise always preview black and white. The runner adds them to the booklet jobs.
- **`src/lib/themedTemplates.ts` is the rest of that range** (crosses, landscapes, sport, music, heritage covers — Celtic Cross, Golden Sunset, Golf, Grand Piano, Guyana Thanksgiving, …), built on the classic family's helpers (`buildDesignPages`, `fixed`/`field`, …). Two kinds of artwork, kept apart on purpose: **flat, many-coloured artwork** (flags, rainbow, sunbursts, candles, sports kit, the karate silhouette) is SVG under `public/elements/templates/` — and the owner's own cutouts (the Jamaican butterfly, and the ghosted Bob Marley portrait, which sits between the cover's ground and borders through the design's `coverChrome`; transparent PNGs from the owner's PSDs) live beside it; an artwork file a published template has used stays there, since saved designs and order snapshots still draw it —, referenced as a relative `/elements/templates/…` path — it ships with the code, prints as vector, and `sync-templates` never needs to copy it; **photographs** go through the background pipeline, and a design receives their rendered URLs through `ArtworkUrls` so the module stays pure (a spec lists its `backgrounds` so the runner can refuse an unrendered one). A design whose cover ground is too busy for a running order sets its interior on plain paper (`interior`), and one whose middle isn't clear moves its farewell (`backTop`). The `ember`/`periwinkle`/`noir` palettes are grounds a photograph fades into, not page palettes. The Cultural and Music categories were added for these — a fresh database gets them from the seed; production needs them created in `/admin` before a sync.

## Background Artwork

The raster route around the vector ceiling above: real public-domain and free-licence pictures (Redouté botanicals, Japanese florals, stock skies) rendered as a **locked, full-bleed image behind the template**. This is what makes two templates look genuinely different at thumbnail size.

- **`locked` elements are template artwork, not customer content.** `ElementBase.locked` (`designEditor.ts`): on the customer path a locked element can't be selected, dragged, resized, edited or deleted and shows no outline — `PageCanvas` renders it inert with `pointer-events: none` so a click on it deselects. Only the authoring editor (`editLocked={authoring}`) can touch it, via the lock toggle in the selection toolbar. `FULL_BLEED_BOX` is the element box that covers the artboard including bleed (slightly negative x/y, >100% w/h) — element coordinates are trim-relative, so a background at 0/0/100/100 would leave a hairline of bare paper at the cut.
- **`src/lib/backgroundArtwork.ts` is pure and unit-tested**: the `BACKGROUND_SPECS` manifest (source ref, licence, credit, crop focus/inset, fade, text zone, palettes), `backgroundAssetKey(id, palette)` (the deterministic key `templates/backgrounds/<id>-<palette>.jpg`, so no index file is needed) and `backgroundElement(url)`. Every manifest entry was verified against its source API; **ids are immutable** because generated templates reference them. Sources: Met Open Access (`met`, no key, refuses non-`isPublicDomain` objects), Wikimedia Commons (`commons`, refuses anything not public domain/CC0), Pexels (`pexels`, needs `PEXELS_API_KEY`), or a plain `url` with a hand-written licence.
- **`npm run backgrounds:fetch`** (`src/db/fetchBackgrounds.ts`, no DB) downloads each source once into `node_modules/.cache/tfs-backgrounds/`, then renders one variant per palette through `src/lib/backgroundRender.server.ts`: a `<canvas>` in the shared headless Chromium (no image library is installed — don't add one) that trims the scan edge (`inset`), cover-crops to the artboard at 300dpi anchored on `focus`, multiplies toward the palette accent (`tint`), washes toward the palette paper (`wash`), and fades to solid paper over the text zone (`fade`). Output goes to S3 when configured, else `public/templates/backgrounds/` (gitignored — local dev output). The licence record goes to the **tracked** `docs/template-artwork-credits.json`, never beside the images, since in S3 mode nothing lands locally; it's rebuilt for the whole manifest on every run (`mergeCredits`), so a `--only` run can't shrink an attribution record down to what it happened to fetch. Tune `focus`/`fade`/`wash` per spec and re-run with `--force` rather than editing images by hand. **Verify a new source visually before adding it** — the crop model assumes a portrait-ish subject on plain ground, which is true of botanical plates and false of folding screens and calligraphy prints (two Japanese entries were dropped for exactly this).
- **Backgrounds render per format.** One A5 render serves every A size; a background with a `bookmark` block (layout overrides, possibly empty) is also rendered at the bookmark's 50 × 200 mm artboard, keyed `<id>-<palette>-bookmark.jpg` (`backgroundAssetKey(id, palette, format)`; the A5 key keeps its old suffix-free form, which every existing template references). A cover crop of the A5 render would keep a sliver of a landscape and an 88 mm-tall flower band. Photographic **scenes** (`scene()` in the manifest) are full-bleed, untinted, and `shade`d toward the top and bottom edges so the white type set on them holds; a plate used only as a cutout (`cutout()`) has no palettes and renders no variants. The fetcher waits out Commons' 429s (`fetchPolitely`) rather than failing the rest of a run.
- **Two artwork families, and the photo-led one is the default.** Real funeral stationery makes the *photograph* the subject and florals the frame — a corner spray, a bottom spray, a diagonal pair — so `SPRAY_COVERS` (`keepsake`, `portrait-corners`, `arch-spray`) puts a large photo on plain paper with a **cutout** accent, and that's what most of `CURATED_ARTWORK` uses. Full-bleed artwork that pushes the photo out reads as a botanical print, not a memorial; keep `artwork`/`artwork-portrait` for plates that can't be cut out. A test enforces that every spray cover has a photo placeholder larger than any single spray on it.
- **Sprays are cutouts, not tinted crops.** `renderSpray` knocks the plate's plain ground to transparent by **flood-filling inward from the image border**, never by a brightness threshold — a white flower on cream paper would lose its petals to a threshold, but its petals aren't connected to the border. `cropBottom` drops the engraved caption first, and `minEnclosedRegion` clears ground pockets the border fill can't reach (the gap framed by crossing stems) while leaving small highlights inside petals alone. Sprays are rendered **once, untinted** (`sprayAssetKey`), not per palette: a cutout keeps the specimen's own colour, and cohesion comes from pairing it with suitable palettes. A plate whose subject sits too close to its ground can't be cut — the Madonna lily is background-only for exactly this reason. Cutouts must use `fit: "contain"` (`ImageElement.fit`), since `object-cover` would crop the silhouette that *is* the artwork.
- **A third family: photographic flower bands** (`band-framed`, `band-oval`, `inset-frame`, `silk-frame` in `ARTWORK_COVERS`). Real flowers along the foot or in one corner of a white page, the framed portrait and type in the clear space above — the look most of the market sells. They are ordinary backgrounds: `placement` + an eased `fade` make a band, `radialFade` tucks a photograph into a corner (a straight `feather` on a corner box still reads as a pasted rectangle), and `glow` washes a colour in from the top edge. The `rose`/`wine`/`violet`/`blue` palettes (white paper) exist for these, and their accents are in `INK_PALETTE` so a customer can recolour back to them. A test keeps band covers' type above the band. **The booklet uses the `-low` versions** (`BOOKLET_BANDS`, `lowBandId`): the same photographs held in the bottom third, because a family's cover needs the church and its address, the committal and the officiating minister (`PLACEHOLDER_SERVICE_FULL`/`PLACEHOLDER_OFFICIANT`), and the back page where everyone gathers afterwards (`PLACEHOLDER_AFTERWARDS`) — the original band rose past half the page and left two lines. The originals stay for the A6 cards and bookmarks, which are composed around them. Changing a background's layout means a **new id**, never a re-render under the old key: `sync-templates.ts` copies only keys production lacks, and a saved design keeps pointing at the old picture. Sources are CC0 Unsplash/Pixabay imports on Commons — search Commons with "unsplash"/"cc0" in the query, since most plain hits are CC BY-SA and the adapter refuses them.
- **`satin` is a generated source, not a fetched one** (`drawSatinInBrowser`): Commons has no usable CC0 satin, so the fold pattern is painted on the canvas from a fixed `seed`. Type on it is light (`LIGHT_TYPE_ARTWORK`), and `TemplateSpec.accent` names a spray to put in its corner — pick a cutout that is clean on a dark ground, since ground specks and highlight holes that white paper hides show on satin.
- **The owner's own photographs are `file` sources**, committed under `assets/backgrounds/` as sRGB JPEGs (their PSDs are CMYK — convert first, e.g. `sips -m "/System/Library/ColorSync/Profiles/sRGB Profile.icc"`). The Orchid, Pink Aura and Pink Roses bands (`orchid-low`, `pink-aura-low`, `pink-rose-low`) and Grand Piano's keys (`piano-hands`) are. A photograph shot on a white ground sets **`onPaper`**, which multiplies it onto the palette paper so its white doesn't show as a whiter strip on a cream page.
- **`mirror`** flips a photograph left to right at render time (the wooden cross that stood on the wrong side); `focus` still refers to the source as taken.
- **Spray cutting has two more knobs**: `spray.monochrome` redraws a coloured study in one ink (the Grey Flora flourish), and `spray.minIsland` drops stray opaque islands — foxing and plate-edge slivers that are darker than the ground, so no tolerance lifts them. Raising `tolerance` to clean a scan is usually wrong: a pale petal that touches the ground through its highlights gets cut too. Prefer `minIsland`, and change one knob per re-render (`--only=<id>`) and look at the result on a dark ground.
- **Template previews show a stand-in portrait; stored layouts never do.** A template's photo windows are empty (`src: null`) so the customer adds their own, but an empty dashed box makes a useless thumbnail. `renderTemplateThumbnail` fills them at screenshot time only (`withPlaceholderPhotos`, `src/lib/placeholderPortraits.ts`), so both the generator and the admin publish flow get it from one place. **Never bake a portrait into a stored layout** — a saved template carrying a stranger's face could be ordered as-is. The set is matched to the cover (`portraitSetForPage`): black-and-white (`portrait-1`–`3`) on a plain paper cover, colour (`portrait-4`–`9`) on one that carries artwork — a monochrome face looks pasted in beside a flower band — and colour on a collage too, so its windows preview as a family rather than a mix. Within the set the portrait is chosen by slug, so a template keeps the same face across republishes, and every page of one template draws from its cover's set. An admin can pin one per template (`templates.placeholder_portrait`, picker on `/admin/templates/[slug]`; null = the automatic pick above) — the pick wins over the cover's set, and saving a change redraws the thumbnail best-effort. Assets live at `templates/placeholders/portrait-<n>.webp` (dev and prod buckets) — the automatic sets (`portrait-1`–`9`, bar `portrait-3`, which already had room) at `portrait-<n>-v2.webp`, outpainted to a looser head and shoulders, since the originals' hair touched a squarer window's frame; a redrawn portrait gets a new key (`placeholderPortraitKey`), never an overwrite. Every stand-in sits a fifth of the way down its window (`PLACEHOLDER_CROP`, y = 20): centred left the hair touching a squarer window's frame, and pinned to the top showed only hair-to-nose in the board collage's wide windows. They are AI-generated, so no real person's likeness is involved. A third set, the studio portraits (`STUDIO_PORTRAIT_IDS`, `portrait-10`–`21`), is never dealt out automatically — adding it changed no existing template's face — and is pinned per themed template; each records its gender (`STUDIO_PORTRAIT_GENDER`), and the themed family renames its sample person to match (`STUDIO_PEOPLE`, `personalise()` rewrites the name, nickname and "wife"/"husband" wording), so a template's preview never puts a man's face over a woman's name. A fourth set, the subject portraits (`SUBJECT_PORTRAIT_IDS`, `portrait-22`–`26`: a baby, two rabbits, a dog, a cat), does the same for the Child and Pets covers (`SUBJECT_PEOPLE`; a pet has no gender). They are CC0 photographs, credited in `docs/placeholder-portrait-credits.md`. A fifth set, the older studio portraits (`ELDER_PORTRAIT_IDS`, `portrait-27`–`38`), is the studio set's twelve people aged, in the same order — so `portrait-27` is `portrait-10` older and the genders (`ELDER_PORTRAIT_GENDER`) match one for one; never dealt out automatically, and unlike the studio set it is offered in the admin picker. The themed family pins the older twin where the theme reads as a long life (the faith, heritage and landscape covers, piano, golf, cricket, reading) and the younger one where it reads young (most sport, Bob Marley, LGBT, guitar); `ELDER_PEOPLE` names each older face as its twin, so a switch changes no wording. The life stories (`HIS_LIFE_PORTRAIT_IDS` `portrait-39`–`44`, `HER_LIFE_PORTRAIT_IDS` `portrait-45`–`50`) are one person's life for a photo collage: the first of each late in life for the large window, the rest their earlier years in order. They are square scenes, not portraits, so each carries its own crop height (`placeholderCrop`, passed with its URL by `placeholderPortraitSources`): the memory board's 1.86:1 windows show the band with the face, a booklet's squarer windows nearly the whole photo. Pin a set's lead (the picker offers only the leads, as "Life story" options) and the rotation fills the collage in order; never dealt out automatically. `sync-templates` does not copy portrait files — they are not referenced from a layout — so a new portrait is copied to the prod bucket by hand.
- **`npm run templates:thumbnails`** (`src/db/refreshThumbnails.ts`) backfills `preview_image_url` from each template's **live** layout, for rows created any way — seeded, generated, or hand-authored. Use it when something affecting every preview changes; it touches only the preview image, so it is safe against published templates. Needs a running server, same as the generator (`--status=`, `--only=`, `--origin=`).
- **Anything passed to `page.evaluate` that contains an inner function needs the `__name` shim** (`blankPage` in `backgroundRender.server.ts`). tsx/esbuild compiles with keepNames and wraps inner named functions in a `__name(...)` helper that exists in the Node bundle but not in the serialised browser function, so it throws `__name is not defined` without it.
- **Artwork templates use the `artwork` / `artwork-portrait` archetypes** (`ARTWORK_COVERS` in `templateGenerator.ts`) and require `TemplateSpec.background`. They put name and dates in the background's `textZone` and nothing else competes with the picture — no borders or motifs. The background element is always **element 0** on the cover and back page; the middle page is plain paper so the repeating interior stays readable. `buildTemplateLayout(spec, { backgroundUrl })` throws without the URL, for an unknown background, or for a palette the background wasn't rendered for; the runner resolves the URL via `backgroundAssetUrl` and skips a spec whose asset is missing locally with a pointer to `backgrounds:fetch`. Curate `CURATED_ARTWORK` the same way as `CURATED`: one picture per palette, never the same picture twice in one palette.
- Order of operations for a fresh library: `npm run backgrounds:fetch` → `npm run dev` → `npm run templates:generate` → review in `/admin/templates`.

## Deployment

All in Frankfurt / eu-central-1 (TiDB Cloud only offers that EU region): Vercel (`fra1`, `vercel.json`) + TiDB Cloud (MySQL-compatible) + the `funeral-stationery-prod-eu-central-1` S3 bucket (eu-central-1, public-read, CORS for browser PUTs). Local dev keeps its own MySQL and the `myprintshopsaas` bucket.

- **Migrations run on deploy.** Vercel runs `vercel-build` = `scripts/migrate-on-deploy.ts && next build`; the script runs `drizzle-kit migrate` **only when `VERCEL_ENV === "production"`**, so a preview deploy of a branch carrying a new migration can never move the production schema (`ALLOW_PREVIEW_MIGRATIONS=1` is the opt-in for a preview with its *own* database). Still scope `DATABASE_URL` to Production only in Vercel. A failed migration fails the build, so code never goes live against a schema it doesn't match; the other way round, the script refuses to migrate a build `next build` would fail (`deployBlocker` — today the Turnstile site-key check), so a broken build can't leave the live release on a moved schema. CI fails any schema change that arrives without its generated migration — always `npm run db:generate` and commit the result; never `db:push` against production.
- **Links are built on a configured origin, not the request's host.** `resolveRequestOrigin` (`stripe.server.ts` → the pure, tested `siteOrigin.ts`) uses `SITE_URL`, else on a production deploy Vercel's `VERCEL_PROJECT_PRODUCTION_URL`, and only then the request's `x-forwarded-host`. A sender controls that header, so trusting it would let someone have the owner emailed a real sign-in token on their own domain. Scope `SITE_URL` to Production in Vercel; leave it unset locally so ngrok and preview deploys keep following the request. New code that builds an absolute link uses this helper — never `request.url` or the headers directly.
- **TLS is switched on by host.** `src/db/index.ts`, `drizzle.config.ts` and `scripts/copy-catalogue.ts` enable TLS when the host ends in `.tidbcloud.com` (TiDB refuses plaintext); local MySQL stays plaintext.
- **The first production catalogue is copied, not seeded.** `scripts/copy-catalogue.ts` copies products/categories/templates/pricing from a source DB into an empty, migrated target, rewriting the absolute storage URLs in `preview_image_url`/`layout`/`draft_layout` to the new bucket (the objects themselves were copied with `aws s3`). It dry-runs by default and refuses a target that already has products. Anything admin-uploaded later goes to the prod bucket directly.
- **Templates made locally reach prod with `scripts/sync-templates.ts`, not with the merge.** A merge ships code; generated or locally authored templates are rows in the local DB and images in the dev bucket. After the code is deployed, the script compares templates by slug (layouts by content, not key order), copies every referenced storage object into the prod bucket, then upserts the new/changed rows and their category links in one transaction. It dry-runs by default, leaves prod-only templates alone, and skips a template edited in prod more recently unless `--force`. Product and category slugs must already exist in prod.

## Claude Code Execution Directives

1. **Targeted Edits Only:** Do NOT rewrite entire files for localized changes. Use surgical diffs.
2. **Verification Loop:** Run `npm run lint` and `npm test` after changes. There is still no typecheck script — do not invent one or assume it exists (run `npx tsc --noEmit` directly if you need one).
3. **Tests Come With the Change:** New or changed logic gets Vitest coverage in the same commit, and a bug fix gets a test that fails without the fix. Put decisions in a pure module next to its `.server.ts` seam and test them there, as `orders.ts`, `siteAccess.ts` and `thintent.ts` already do. If logic is stuck inside a seam or a route, extract the decision into a pure function rather than leave it untested. Interactive client components are tested with Testing Library under jsdom (see `ConfirmDialog.test.tsx`). Only a route's request/response wiring and the Stripe/DB calls themselves are left untested; nothing mocks the database. Cover those in the feature's manual test plan instead.
4. **No Unrequested Packages:** Never run `npm install` for new libraries unless explicitly requested. (Proof generation, the Drizzle/MySQL data layer, `pdfjs-dist` for the upload preview and `@marsidev/react-turnstile` for the forms' bot check — see **Proof Generation**, **Data Layer**, **Upload Your Own Design** and the Turnstile note under **Shop Front** above — are intentional, already-approved exceptions, not precedent for adding other backend infrastructure unasked. There is still no auth provider — don't add one speculatively.)
5. **Design Fidelity:** When building new UI, check `HANDOFF.md` and the existing `globals.css` tokens and component classes first. Don't hardcode raw hex colors or arbitrary spacing values in components when an equivalent token already exists.
6. **No Ad-Hoc Manual Verification Rigs:** For small, low-risk UI/layout changes, do NOT stand up a throwaway verification rig (spinning up a dev server, screenshotting) just to confirm something answerable by reading the code/diff. Answer directly, or ask the user if they'd rather share a screenshot. Reserve real browser verification for changes where correctness can't be judged by reading the code, and even then, ask first before standing up that kind of rig.
